# 블록 매치 설계 문서

2인 대전 블록 퍼즐 게임. 두 플레이어가 각자의 8×8 보드에 동시에 블록을 놓아 개인 점수를 겨룬다.
제안서의 개발 일정 중 **10주차(프로젝트 설계 및 기본 게임 화면 구현)** 시점에 작성했다.

## 1. 제안서에서 정리가 필요했던 점

제안서 본문과 예상 GUI가 서로 다르다. 팀 확인 전까지는 아래 기준으로 진행한다.

| 항목 | 제안서 본문 | 예상 GUI | 현재 기준 |
| --- | --- | --- | --- |
| 게임 방식 | 협동, 공동 점수 | 1:1 대전, 개인 점수 | 1:1 대전 (예상 GUI) |
| 보드 | 공유 보드 1개 | 내 보드 + 상대 보드 | 내 보드 + 상대 보드 (예상 GUI) |
| 진행 | 턴제 | 제한 시간 표시 | 실시간, 제한 시간 종료 (예상 GUI) |
| 화면 스타일 | 없음 | 남색 보드, 파스텔 블록, 가로 모드 | 10주차는 가로 배치만, 스타일은 이후 적용 |
| 게임 이름 | Block Blast Duo | 블록 매치 | 블록 매치 |

게임 이름은 기존 상용 게임의 이름을 쓰지 않기 위해 예상 GUI의 "블록 매치"로 정했다.

게임은 제한 시간 120초(`GameConfig.TIME_LIMIT_SECONDS`)가 끝나면 종료되고, 점수가 높은 플레이어가 이긴다. 동점이면 무승부다.
블록을 놓을 곳이 없는 플레이어는 시간이 끝날 때까지 기다리며, 그때까지의 점수로 승패를 가린다.

블록과 점수 규칙 (`GameRules`):

- 블록을 놓으면 놓은 칸 수 × 10점을 얻는다.
- 가로줄이나 세로줄이 가득 차면 그 줄을 지우고, 지운 줄 수 × 100 × 지운 줄 수만큼 더 얻는다. (1줄 100점, 2줄 400점, 3줄 900점)
- 가득 찬 가로줄과 세로줄을 모두 찾은 뒤 한꺼번에 지운다. 겹치는 칸은 한 번만 지우고, 줄 수는 가로와 세로를 각각 센다.
- 블록 3개를 모두 쓰면 무작위로 새 블록 3개를 받는다. 놓을 수 있는 블록이 나오도록 보장하지는 않는다.

## 2. 모듈 구성

| 모듈 | 역할 | 의존성 |
| --- | --- | --- |
| `Common` | 공용 모델(보드, 블록, 게임 상태), 설계 문서 | 없음 |
| `Client` | Swing 화면, 입력 처리, 서버 통신 | `Common` |
| `Server` | 접속 관리, 게임 진행, 메시지 중계 | `Common` |

세 모듈을 하나의 저장소에 두고 IntelliJ에서 하나의 프로젝트로 연다.

`Common`을 분리한 이유는 클라이언트와 서버가 같은 규칙과 데이터를 봐야 하기 때문이다.
복사해서 쓰면 한쪽만 수정되어 동기화 오류가 생기기 쉽다.

## 3. 전체 구조

```text
┌─ Client (정동오) ──┐                       ┌─ Client (박성훈) ──┐
│ GameFrame (Swing) │                       │ GameFrame (Swing) │
│ 수신 스레드        │                       │ 수신 스레드        │
└────────┬──────────┘                       └─────────┬─────────┘
         │              TCP Socket (포트 30000)        │
         └───────────────────┐   ┌────────────────────┘
                             ▼   ▼
                    ┌─ Server ─────────────┐
                    │ 접속 대기 스레드       │
                    │ 플레이어별 스레드 × 2  │
                    │ 게임 상태 원본         │
                    └──────────────────────┘
```

- **서버가 게임 상태의 원본을 갖는다.** 클라이언트는 "여기에 놓겠다"고 요청만 하고, 판정은 서버가 한다.
  두 화면이 어긋나지 않고, 규칙에 맞지 않는 입력도 서버에서 막을 수 있다.
- **화면은 `GameState`만 보고 그린다.** 11주차부터 화면을 `GameState`에 연결하고, 상태가 바뀌면 다시 그린다.
  이렇게 하면 12주차에 상태의 출처만 서버로 바꾸면 된다.

## 4. 클래스 구조

10주차에 만든 클래스:

| 모듈 | 클래스 | 역할 |
| --- | --- | --- |
| Common | `GameConfig` | 보드 크기, 블록 개수, 제한 시간, 기본 포트 |
| Common | `Board` | 8×8 칸 데이터 |
| Common | `BlockShape` | 블록 모양과 색상 번호 |
| Common | `PlayerState` | 플레이어별 이름, 보드, 점수, 현재 블록 |
| Common | `GameState` | 플레이어 2명의 상태 |
| Client | `ClientMain` | 진입점 |
| Client | `ui.GameFrame` | 메인 창, 내 보드와 상대 보드 배치 |
| Client | `ui.PlayerInfoPanel` | 보드 위 플레이어 닉네임과 점수 자리 |
| Client | `ui.BoardPanel` | 8×8 격자 |
| Client | `ui.BlockTrayPanel` | 블록 3개가 들어갈 칸 |
| Client | `ui.ChatPanel` | 채팅 영역, 서버 접속 상태 표시 (전송 기능 없음) |
| Server | `ServerMain` | 진입점 (12주차 구현 예정) |

10주차 화면은 영역 배치만 잡은 틀이다. 공용 모델은 아직 화면과 연결하지 않았고, 예상 GUI의 스타일은 이후 UI 개선 단계에서 적용한다.

Wireshark 과제를 위해 12주차 소켓 통신 중 접속 과정을 먼저 구현했다:

| 모듈 | 클래스 | 역할 |
| --- | --- | --- |
| Common | `Protocol` | 메시지 형식, 변환 (`JOIN`, `WELCOME`, `START`만) |
| Server | `GameServer` | 접속 수락, 두 명 입장 시 게임 시작 |
| Server | `ClientHandler` | 플레이어별 수신, 송신 |
| Client | `ServerConnection` | 서버 연결, 수신 스레드 |

11주차에 만든 클래스 (서버 연동 전이라 내 보드에서 혼자 플레이한다):

| 모듈 | 클래스 | 역할 |
| --- | --- | --- |
| Common | `GameRules` | 배치 가능 판정, 배치, 줄 제거, 점수 계산, 블록 채우기 |
| Client | `ui.Theme` | 블록 색상, 블록 칸 그리기 |
| Client | `ui.BlockDragHandler` | 트레이의 블록을 마우스로 끌어 보드에 놓기, 놓을 자리 미리보기 |

`BoardPanel`, `BlockTrayPanel`, `PlayerInfoPanel`은 `GameState`를 보고 보드, 블록, 점수를 그리도록 바꿨다.

앞으로 추가할 클래스:

| 주차 | 모듈 | 클래스 | 역할 |
| --- | --- | --- | --- |
| 12 | Common | `Protocol` 확장 | 나머지 메시지 추가 |
| 12 | Server | `GameRoom` | 게임 진행, 제한 시간, 승패 판정 |

## 5. 스레드 구조

| 위치 | 스레드 | 하는 일 |
| --- | --- | --- |
| Server | 접속 대기 | `ServerSocket.accept()` 후 플레이어별 스레드 생성 |
| Server | 플레이어별 | 메시지 수신. `GameRoom` 접근은 `synchronized`로 보호 |
| Server | 타이머 | 제한 시간이 끝나면 `GameRoom`을 종료하고 `GAMEOVER` 전송 |
| Client | EDT | 화면 그리기, 마우스와 키보드 입력 |
| Client | 수신 | 서버 메시지 수신 후 `SwingUtilities.invokeLater`로 화면 갱신 |

Swing 컴포넌트는 EDT에서만 변경한다. 수신 스레드에서 직접 화면을 바꾸면 안 된다.

## 6. 통신 프로토콜 초안

제안서대로 `BufferedReader`/`BufferedWriter`를 사용하고, 한 줄이 메시지 하나다.
형식은 `종류|값1|값2`이며 12주차 구현 때 확정한다.

| 방향 | 메시지 | 의미 |
| --- | --- | --- |
| C → S | `JOIN\|이름` | 입장 |
| S → C | `WELCOME\|내번호` | 입장 승인, 플레이어 번호(0 또는 1) |
| S → C | `START\|이름0\|이름1\|제한시간초` | 두 명이 모여 게임 시작 |
| C → S | `PLACE\|블록칸\|행\|열` | 블록 배치 요청 |
| S → C | `STATE\|점수0\|보드0\|블록들0\|점수1\|보드1\|블록들1` | 두 플레이어의 게임 상태 전체 |
| S → C | `REJECT\|사유` | 배치 거부 |
| C → S | `CHAT\|내용` | 채팅 전송 |
| S → C | `CHAT\|이름\|내용` | 채팅 전달 |
| S → C | `GAMEOVER\|점수0\|점수1` | 게임 종료, 플레이어별 최종 점수 |

- 채팅 내용에 `|`가 들어갈 수 있으므로 `split("\\|", 최대개수)`로 나눈다.
- 제한 시간은 서버가 관리한다. 클라이언트의 남은 시간 표시는 `START`를 받은 시점부터 계산하고, 종료는 `GAMEOVER`로 판단한다.
- 부분 변경 대신 `STATE` 전체를 보내 구현을 단순하게 유지한다. 메시지가 짧아서 부담이 없다.

### 블록 배치 흐름

```text
플레이어               서버                     두 클라이언트
    │ PLACE|0|3|2       │                            │
    ├──────────────────▶│ GameRules로 판정            │
    │                   │ 성공: 상태 변경             │
    │                   ├─ STATE ───────────────────▶│ 화면 갱신
    │◀─ REJECT ─────────┤ 실패: 요청자에게만 전달      │
```
