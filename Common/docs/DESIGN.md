# 블록 매치 설계 문서

2인 대전 블록 퍼즐 게임. 두 플레이어가 각자의 8×8 보드에 동시에 블록을 놓아 개인 점수를 겨룬다.
제안서의 개발 일정 중 **10주차(프로젝트 설계 및 기본 게임 화면 구현)** 시점에 작성했다.

## 1. 제안서에서 정리가 필요했던 점

제안서 본문과 예상 GUI가 서로 다르다. 팀 확인 전까지는 아래 기준으로 진행한다.

| 항목 | 제안서 본문 | 예상 GUI | 현재 기준 |
| --- | --- | --- | --- |
| 게임 방식 | 협동, 공동 점수 | 1:1 대전, 개인 점수 | 1:1 대전 (예상 GUI) |
| 보드 | 공유 보드 1개 | 내 보드 + 상대 보드 | 내 보드 + 상대 보드 (예상 GUI) |
| 진행 | 턴제 | 제한 시간 표시 | 실시간, 제한 시간 종료 (예상 GUI) |
| 화면 스타일 | 없음 | 남색 보드, 파스텔 블록, 가로 모드 | 예상 GUI 스타일 적용 |
| 게임 이름 | Block Blast Duo | 블록 매치 | 블록 매치 |

게임 이름은 기존 상용 게임의 이름을 쓰지 않기 위해 예상 GUI의 "블록 매치"로 정했다.

게임은 두 가지 경우에 끝난다.

- 제한 시간 5분(`GameConfig.TIME_LIMIT_SECONDS`, 300초)이 끝나면 점수가 높은 플레이어가 이긴다. 동점이면 무승부다.
- 시간이 끝나기 전에 한 플레이어가 남은 블록을 하나도 놓을 수 없게 되면, 그 즉시 그 플레이어가 지고 게임이 끝난다.

블록과 점수 규칙 (`GameRules`):

- 블록을 놓으면 놓은 칸 수 × 10점을 얻는다.
- 가로줄이나 세로줄이 가득 차면 그 줄을 지우고, 지운 줄 수 × 100 × 지운 줄 수만큼 더 얻는다. (1줄 100점, 2줄 400점, 3줄 900점)
- 가득 찬 가로줄과 세로줄을 모두 찾은 뒤 한꺼번에 지운다. 겹치는 칸은 한 번만 지우고, 줄 수는 가로와 세로를 각각 센다.
- 블록 3개를 모두 쓰면 새 블록 3개를 받는다. 그 순간의 보드에 놓을 자리가 있는 모양 중에서만 무작위로 고르므로, 받은 블록 3개는 각각 놓을 수 있다. 다만 세 블록을 모두 놓을 수 있는 순서까지는 보장하지 않아서, 앞의 블록을 잘못 놓으면 나머지 블록을 놓을 곳이 없어질 수 있다(그러면 위의 규칙대로 진다).

## 2. 모듈 구성

| 모듈 | 역할 | 의존성 |
| --- | --- | --- |
| `Common` | 공용 모델(보드, 블록, 게임 상태), 설계 문서 | 없음 |
| `Client` | Swing 화면, 입력 처리, 서버 통신 | `Common` |
| `Server` | 접속 관리, 게임 진행, 메시지 중계 | `Common` |

세 모듈을 하나의 저장소에 두고 IntelliJ에서 하나의 프로젝트로 연다.

`Common`을 분리한 이유는 클라이언트와 서버가 같은 규칙과 데이터를 봐야 하기 때문이다.
복사해서 쓰면 한쪽만 수정되어 동기화 오류가 생기기 쉽다.

## 3. 전체 구조

```text
┌─ Client (정동오) ──┐                       ┌─ Client (박성훈) ──┐
│ GameFrame (Swing) │                       │ GameFrame (Swing) │
│ 수신 스레드        │                       │ 수신 스레드        │
└────────┬──────────┘                       └─────────┬─────────┘
         │              TCP Socket (포트 30000)        │
         └───────────────────┐   ┌────────────────────┘
                             ▼   ▼
                    ┌─ Server ─────────────┐
                    │ 접속 대기 스레드       │
                    │ 플레이어별 스레드 × 2  │
                    │ 게임 상태 원본         │
                    └──────────────────────┘
```

- **서버가 게임 상태의 원본을 갖는다.** 클라이언트는 "여기에 놓겠다"고 요청만 하고, 판정은 서버가 한다.
  두 화면이 어긋나지 않고, 규칙에 맞지 않는 입력도 서버에서 막을 수 있다.
- **화면은 `GameState`만 보고 그린다.** 11주차부터 화면을 `GameState`에 연결하고, 상태가 바뀌면 다시 그린다.
  이렇게 하면 12주차에 상태의 출처만 서버로 바꾸면 된다.

## 4. 클래스 구조

10주차에 만든 클래스:

| 모듈 | 클래스 | 역할 |
| --- | --- | --- |
| Common | `GameConfig` | 보드 크기, 블록 개수, 제한 시간, 기본 포트 |
| Common | `Board` | 8×8 칸 데이터 |
| Common | `BlockShape` | 블록 모양과 색상 번호 |
| Common | `PlayerState` | 플레이어별 이름, 보드, 점수, 현재 블록 |
| Common | `GameState` | 플레이어 2명의 상태 |
| Client | `ClientMain` | 진입점 |
| Client | `ui.GameFrame` | 메인 창, 내 보드와 상대 보드 배치 |
| Client | `ui.PlayerInfoPanel` | 보드 위 플레이어 닉네임과 점수 자리 |
| Client | `ui.BoardPanel` | 8×8 격자 |
| Client | `ui.BlockTrayPanel` | 블록 3개가 들어갈 칸 |
| Client | `ui.ChatPanel` | 채팅 영역, 서버 접속 상태와 채팅 표시, 채팅 입력과 전송 (11주차에 연결) |
| Server | `ServerMain` | 진입점 |

10주차 화면은 영역 배치만 잡은 틀이다. 공용 모델은 아직 화면과 연결하지 않았고, 예상 GUI의 스타일은 이후 UI 개선 단계에서 적용한다.

Wireshark 과제를 위해 12주차 소켓 통신 중 접속 과정을 먼저 구현했다:

| 모듈 | 클래스 | 역할 |
| --- | --- | --- |
| Common | `Protocol` | 메시지 형식, 변환 (`JOIN`, `WELCOME`, `START`만) |
| Server | `GameServer` | 접속 수락, 두 명 입장 시 게임 시작 |
| Server | `ClientHandler` | 플레이어별 수신, 송신 |
| Client | `ServerConnection` | 서버 연결, 수신 스레드 |

11주차에 만든 클래스 (서버 연동 전이라 내 보드에서 혼자 플레이한다):

| 모듈 | 클래스 | 역할 |
| --- | --- | --- |
| Common | `GameRules` | 배치 가능 판정, 배치, 줄 제거, 점수 계산, 블록 채우기 |
| Client | `ui.Theme` | 블록 색상, 블록 칸 그리기 |
| Client | `ui.BlockDragHandler` | 트레이의 블록을 마우스로 끌어 보드에 놓기, 놓을 자리 미리보기 |

`BoardPanel`, `BlockTrayPanel`, `PlayerInfoPanel`은 `GameState`를 보고 보드, 블록, 점수를 그리도록 바꿨다.

12주차에 만든 클래스 (서버가 게임 상태의 원본을 갖는 대전):

| 모듈 | 클래스 | 역할 |
| --- | --- | --- |
| Common | `Protocol` 확장 | `PLACE`, `STATE` 메시지, `STATE` 만들기(`encodeState`)와 읽기(`readPlayer`) |
| Server | `GameRoom` | 게임 한 판의 상태 원본, `GameRules`로 배치 판정, 제한 시간과 승패 판정 |
| Client | `ui.MatchStatusPanel` | 두 보드 사이에 남은 시간과 결과(승리/패배/무승부) 표시 |
| Client | `GameSession` | 서버의 `WELCOME`, `START`, `STATE`를 화면용 `GameState`에 반영 (0번이 항상 나) |

`BlockDragHandler`는 직접 놓지 않고 `PLACE`를 보내며, `GameFrame`은 받은 상태로 두 보드와 점수를 다시 그린다.

같은 주에 제한 시간과 게임 종료를 추가했다. 서버의 타이머 스레드가 제한 시간이 끝나면 `GameRoom`의 승패를 정하고 `GAMEOVER`를 보낸다. 블록을 놓을 때마다 그 플레이어가 남은 블록을 놓을 수 있는지 확인하고, 하나도 놓을 수 없으면 바로 `GAMEOVER`를 보낸다. 새 블록은 `GameRules`가 놓을 수 있는 모양 중에서만 고른다.

서버는 실행 인자로 제한 시간(초)을 받을 수 있다. 생략하면 5분이다. 시험이나 시연에서 짧게 확인할 때 쓴다.

이어서 메인 화면을 추가했다:

| 모듈 | 클래스 | 역할 |
| --- | --- | --- |
| Client | `ui.MainFrame` | 메인 화면. 게임 이름, 닉네임 입력 칸, 게임 시작 버튼, 안내 문구(지난 게임 결과, 접속 실패 이유) |
| Client | `ClientApp` | 메인 화면 ↔ 게임 화면 전환. 시작하면 게임 창을 만들고 서버에 접속하며, 끝나면 연결을 끊고 메인 화면으로 돌아온다 |

- 닉네임 규칙(비어 있지 않음, 10자 이하, `|` 없음)은 `Protocol.isValidNickname`에 두고 메인 화면과 서버가 함께 쓴다.
- 메인 화면으로 돌아오는 경우: 결과 창의 메인으로 돌아가기, 입장 거부(`BAD_NAME`, `ROOM_FULL`), 접속 실패나 연결 끊김, 게임 창 닫기. 게임 창을 닫아도 프로그램은 끝나지 않는다.
- 메인 화면으로 돌아간 뒤 같은 닉네임으로 다시 시작하면 끝난 게임이 아니라 새 게임에 들어간다. 끝난 게임의 방은 한 명이 나가는 순간 비워진다.

기능 구현 뒤 화면을 예상 GUI(피그마 초안) 스타일로 바꿨다:

| 모듈 | 클래스 | 역할 |
| --- | --- | --- |
| Client | `ui.Theme` 확장 | 화면 전체의 색, 글꼴, 카드와 블록 칸·미리보기 그리기 |
| Client | `ui.PlayArea` | 내 화면, 가운데 영역, 상대 화면의 크기와 위치를 맞춘다 |
| Client | `ui.PlayerColumn` | 플레이어 한 명의 화면 (정보, 보드 이름과 상태, 보드, 트레이) |
| Client | `ui.MatchStatusPanel` 확장 | 게임 이름, 남은 시간, 방금 얻은 점수와 지운 줄 수, 결과, 버튼 |
| Client | `ui.IconButton`, `ui.RoundButton`, `ui.RoundTextField`, `ui.GameDialog` | 둥근 버튼, 입력 칸, 알림 창 |
| Client | `ui.Emoticon` | 이모티콘 4개. 문자로 보내고 화면에는 직접 그린 얼굴을 보여 준다 |

- 이미지 파일 없이 모두 Java2D로 그린다. 프로필 사진 대신 닉네임 첫 글자를 넣은 아바타를 쓴다.
- 초안의 콤보 자리에는 규칙에 있는 값만 표시한다. 한 번에 얻은 점수와 지운 줄 수이며, 줄 수는 점수 차이에서 구한다(`GameRules.clearedLines`).
- 초안에는 상대 트레이가 없지만, 상대의 블록도 보이도록 그대로 둔다.
- 초안의 설정 버튼 자리에는 메인 화면으로 나가는 버튼을 둔다. 게임 중에는 한 번 더 묻는다.

줄 삭제 효과를 추가했다:

| 모듈 | 클래스 | 역할 |
| --- | --- | --- |
| Common | `PlaceResult` | 배치 결과: 얻은 점수, 지운 줄, 지우기 직전의 칸 색 |
| Client | `ui.BoardEffects` | 보드 하나의 효과를 모아 약 60FPS 타이머로 실행하고 끝나면 멈춤 |
| Client | `ui.ClearEffect`, `ui.ParticleSystem`, `ui.Particle`, `ui.FloatingText` | 반짝임·줄 빛·흔들림, 블록 조각, 점수·콤보 글자 |
| Client | `ui.SoundManager` | 코드로 만든 효과음을 별도 스레드에서 재생 |
| Client | `ui.EffectConfig` | 효과의 시간, 개수, 세기 상수 |

이어서 게임이 끝난 뒤 같은 상대와 다시 할 수 있게 했다:

| 모듈 | 클래스 | 역할 |
| --- | --- | --- |
| Common | `Protocol` 확장 | `REMATCH` 메시지 |
| Server | `GameServer` 확장 | 게임이 끝나도 두 플레이어를 자리에 남겨 두고, 둘 다 `REMATCH`를 보내면 새 `GameRoom`으로 다시 시작 |
| Client | `ui.ResultDialog` | 결과 창. "다시 게임하기"와 "메인으로 돌아가기" 버튼, 상대 상황에 따라 바뀌는 안내 문구 |

- 결과 창은 모달이 아니다. 열려 있는 동안 상대의 요청이나 나감을 바로 반영하고, 뒤의 게임 창에서 채팅도 할 수 있다.
- 먼저 누른 사람에게는 "상대방을 기다리는 중...", 상대에게는 "(이름)님: 한판 더해요!"가 보인다. 둘 다 누르면 서버가 `START`와 `STATE`를 보내고, 같은 게임 창에서 결과 창을 닫고 새 게임을 시작한다.
- 결과 창에서 한 명이 메인으로 돌아가거나 창을 닫으면, 남은 사람의 결과 창에 "상대방이 나갔습니다."가 뜨고 다시 게임하기 버튼은 눌리지 않는다. 메인으로 돌아가기만 할 수 있다.
- 게임 중에 상대가 나간 채로 게임이 끝나도 처음부터 다시 게임하기를 누를 수 없다.

## 5. 스레드 구조

| 위치 | 스레드 | 하는 일 |
| --- | --- | --- |
| Server | 접속 대기 | `ServerSocket.accept()` 후 플레이어별 스레드 생성 |
| Server | 플레이어별 | 메시지 수신. `GameRoom` 접근은 `synchronized`로 보호 |
| Server | 타이머 | 제한 시간이 끝나면 `GameRoom`을 종료하고 `GAMEOVER` 전송 |
| Client | EDT | 화면 그리기, 마우스와 키보드 입력 |
| Client | 수신 | 서버 메시지 수신 후 `SwingUtilities.invokeLater`로 화면 갱신 |

Swing 컴포넌트는 EDT에서만 변경한다. 수신 스레드에서 직접 화면을 바꾸면 안 된다.

## 6. 통신 프로토콜

제안서대로 `BufferedReader`/`BufferedWriter`를 사용하고, 한 줄이 메시지 하나다.
형식은 `종류|값1|값2`이다. 아래 메시지는 모두 구현되어 있다.

| 방향 | 메시지 | 의미 |
| --- | --- | --- |
| C → S | `JOIN\|이름` | 입장 |
| S → C | `WELCOME\|내번호` | 입장 승인, 플레이어 번호(0 또는 1) |
| S → C | `START\|이름0\|이름1\|남은시간초` | 두 명이 모여 게임 시작 (다시 들어온 경우에는 남은 시간) |
| C → S | `PLACE\|블록칸\|행\|열` | 블록 배치 요청 |
| S → C | `STATE\|점수0\|보드0\|블록들0\|점수1\|보드1\|블록들1` | 두 플레이어의 게임 상태 전체 |
| S → C | `PLACED\|번호\|획득점수\|콤보\|가로줄\|세로줄\|지운칸` | 블록이 놓임. `STATE`보다 먼저 보내며 화면 효과에만 씀 |
| S → C | `REJECT\|사유` | 배치 거부 |
| C → S | `CHAT\|내용` | 채팅 전송 |
| S → C | `CHAT\|이름\|내용` | 채팅 전달 |
| S → C | `GAMEOVER\|승자번호\|사유\|점수0\|점수1` | 게임 종료. 승자번호는 0, 1 또는 무승부 -1. 사유는 `TIME_UP`(시간 종료) 또는 `NO_MOVES`(진 쪽이 놓을 블록이 없음) |
| S → C | `LEAVE\|이름` | 게임 중이나 게임이 끝난 뒤 결과 창에서 상대의 연결이 끊김 (남은 플레이어에게만) |
| S → C | `REJOIN\|이름` | 나간 자리에 플레이어가 다시 들어옴 (남은 플레이어에게만) |
| C → S | `REMATCH` | 게임이 끝난 뒤 같은 상대와 다시 하기 요청 |
| S → C | `REMATCH\|이름` | 그 이름의 플레이어가 다시 하기를 누름 (두 플레이어 모두에게). 둘 다 누르면 대신 `START`와 `STATE`를 보낸다 |

`REJECT`의 사유 코드는 `BAD_NAME`(닉네임이 비었거나 10자 초과, `\|` 포함, 이미 사용 중), `BAD_REQUEST`, `CANNOT_PLACE`, `NOT_PLAYING`, `ROOM_FULL`(두 자리가 모두 참)이다.

- 채팅 내용에 `|`가 들어갈 수 있으므로 `split("\\|", 최대개수)`로 나눈다.
- 제한 시간은 서버가 관리한다. 클라이언트의 남은 시간 표시는 `START`를 받은 시점부터 계산하고, 종료는 `GAMEOVER`로 판단한다. 클라이언트 시계는 서버보다 조금 늦게 시작하므로, 시간 종료로 끝나면 화면 시계를 00:00으로 맞춘다.
- `GAMEOVER`를 보낸 뒤에도 서버는 두 플레이어를 자리에 남겨 두고 `REMATCH`를 기다린다. 이때 `CHAT`은 그대로 전달하고, `PLACE`는 `NOT_PLAYING`으로 거부한다. 게임 중에 보낸 `REMATCH`도 `NOT_PLAYING`으로 거부한다.
- 끝난 뒤 한 명이 나가면 남은 사람에게 `LEAVE`를 보내고 방을 비운다. 끝난 게임에는 다시 들어올 수 없으므로 남은 사람의 `REMATCH`는 `NOT_PLAYING`으로 거부되고, 새로 들어오는 사람은 새 게임을 기다린다. 게임 중에 한 명이 나간 채로 끝나면 `GAMEOVER`를 보낸 즉시 방을 비운다.
- 부분 변경 대신 `STATE` 전체를 보내 구현을 단순하게 유지한다. 메시지가 짧아서 부담이 없다.
- `STATE`의 보드는 64칸의 색상 번호(빈 칸은 0)를 한 줄로 이어 붙인 문자열이고, 블록들은 `T,SQUARE2,-`처럼 블록 이름을 쉼표로 잇는다. `-`는 이미 사용한 칸이다.
- `PLACED`의 가로줄·세로줄은 지운 줄의 비트 값(r번째 비트가 r행)이고, 지운칸은 보드와 같은 64글자로 지운 칸만 지우기 전 색상 번호를 갖는다. 방금 놓자마자 지워진 칸은 `STATE`를 비교해서는 알 수 없어 따로 보낸다. 콤보는 서버가 센 "연속으로 줄을 지운 배치 횟수"이며 점수에는 영향이 없다. 배치할 때만 보내므로 재접속이나 게임 시작 때는 지난 효과가 다시 나오지 않는다.
- 플레이어 번호는 서버 기준이다. 클라이언트는 `WELCOME`으로 받은 내 번호를 이용해 `STATE`의 내 몫은 "내 보드"에, 상대 몫은 "상대 보드"에 그린다.
- `STATE`는 게임이 시작될 때(`START` 직후, 다시 하기 포함), 블록을 놓았을 때, 나갔던 플레이어가 다시 들어왔을 때 보낸다. 다시 들어온 플레이어는 보드와 점수를 이어받는다.

플레이어               서버                     두 클라이언트
